# AI Courtroom: Agent Communication Protocols

## 1. Title

AI Courtroom: Agent Communication Protocols

## 2. Introduction

All communication within the AI Courtroom simulation is centralized and mediated by the `CourtroomSimulationManagerAgent` (hereafter "Manager"). No child agent (e.g., `JudgeAgent`, `PlaintiffCounselAgent`, `DefendantCounselAgent`) communicates directly with another child agent. This centralized model ensures a structured flow of information, allows for comprehensive logging, and simplifies the interaction logic for each specialized agent.

The purpose of this document is to define the structure and content of the messages exchanged between the Manager and the child agents, as well as messages the Manager might send to the user interface or logging systems. These protocols form the "API" for inter-agent communication, ensuring clarity and consistency.

## 3. General Message Structure (JSON)

All messages exchanged within the system will adhere to a common JSON structure to ensure consistency and ease of parsing.

```json
{
  "sender_agent_id": "string",
  "receiver_agent_id": "string",
  "message_id": "string (UUID, optional but recommended for tracing)",
  "message_type": "string (enum: 'CONTROL', 'DATA', 'QUERY', 'RESPONSE', 'STATUS', 'ERROR')",
  "event_type": "string",
  "payload": {
    // Message-specific content, can be any valid JSON object or null
  },
  "timestamp": "ISO 8601 string (e.g., '2024-07-30T10:30:00Z')"
}
```

**Explanation of Common Fields:**

*   `sender_agent_id`: (string) The unique identifier of the agent sending the message (e.g., `"PlaintiffCounselAgent"`, `"CourtroomSimulationManagerAgent"`, `"JudgeAgent"`).
*   `receiver_agent_id`: (string) The unique identifier of the agent intended to receive the message (e.g., `"CourtroomSimulationManagerAgent"`, `"DefendantCounselAgent"`, `"UserInterface"`).
*   `message_id`: (string, optional) A unique identifier for the message itself (e.g., a UUID). Useful for tracing, logging, and debugging complex interactions.
*   `message_type`: (string, enum) Categorizes the general purpose of the message:
    *   `CONTROL`: Messages that direct the flow of the simulation or instruct an agent to perform a specific action (e.g., start a phase, end turn).
    *   `DATA`: Messages primarily carrying substantive content generated by an agent (e.g., an argument, a verdict).
    *   `QUERY`: Messages that request information or action from another agent (e.g., Judge asking a question, Manager requesting legal knowledge).
    *   `RESPONSE`: Messages that reply to a `QUERY` or acknowledge a `CONTROL` message.
    *   `STATUS`: Messages that provide updates on an agent's internal state or the simulation's progress.
    *   `ERROR`: Messages used to report errors encountered by an agent.
*   `event_type`: (string) A more specific descriptor of the message's intent or the event it represents, providing context for the `payload`. Examples include `"PROMPT_FOR_OPENING_STATEMENT"`, `"ARGUMENT_SUBMITTED"`, `"VERDICT_DELIVERED_BY_JUDGE"`.
*   `payload`: (object | null) A JSON object containing the specific data relevant to the `event_type`. The structure of the payload will vary depending on the message. It can be `null` if the `event_type` itself is sufficient (e.g., for a simple acknowledgment).
*   `timestamp`: (string) An ISO 8601 formatted timestamp indicating when the message was created. Essential for logging and reconstructing event sequences.

## 4. Specific Message Examples for Key Interactions (Illustrative Payloads)

Below are examples of messages for typical interactions. `sender_agent_id`, `receiver_agent_id`, `message_id`, and `timestamp` would be populated appropriately for each.

### 4.1. Manager to Counsel (Start Turn)

*   **Purpose:** Instructs a counsel agent to begin a specific phase of their presentation.
*   **Message:**
    ```json
    {
      "sender_agent_id": "CourtroomSimulationManagerAgent",
      "receiver_agent_id": "PlaintiffCounselAgent",
      "message_type": "CONTROL",
      "event_type": "PROMPT_FOR_ARGUMENT",
      "payload": {
        "phase": "MAIN_ARGUMENT",
        "time_limit_seconds": 120,
        "case_context": { /* relevant case details, prior arguments if any */ }
      },
      "timestamp": "..."
    }
    ```

### 4.2. Counsel to Manager (Submit Argument)

*   **Purpose:** A counsel agent submits its formulated argument to the Manager.
*   **Message:**
    ```json
    {
      "sender_agent_id": "PlaintiffCounselAgent",
      "receiver_agent_id": "CourtroomSimulationManagerAgent",
      "message_type": "DATA",
      "event_type": "ARGUMENT_SUBMITTED",
      "payload": {
        "argument_text": "The defendant's actions clearly demonstrate a breach of contract...",
        "supporting_evidence_refs": ["Exhibit A (Contract)", "Email_Chain_March_15"]
      },
      "timestamp": "..."
    }
    ```

### 4.3. Manager to Judge (Relay Argument)

*   **Purpose:** The Manager relays a counsel's argument to the Judge.
*   **Message:**
    ```json
    {
      "sender_agent_id": "CourtroomSimulationManagerAgent",
      "receiver_agent_id": "JudgeAgent",
      "message_type": "DATA",
      "event_type": "ARGUMENT_RELAYED",
      "payload": {
        "originating_counsel_id": "PlaintiffCounselAgent",
        "argument_text": "The defendant's actions clearly demonstrate a breach of contract...",
        "supporting_evidence_refs": ["Exhibit A (Contract)", "Email_Chain_March_15"]
      },
      "timestamp": "..."
    }
    ```
    *(A similar message would be sent to the opposing counsel for their information)*

### 4.4. Judge to Manager (Ask Question)

*   **Purpose:** The Judge agent poses a question to one of the counsel agents.
*   **Message:**
    ```json
    {
      "sender_agent_id": "JudgeAgent",
      "receiver_agent_id": "CourtroomSimulationManagerAgent",
      "message_type": "QUERY",
      "event_type": "QUESTION_ASKED_BY_JUDGE",
      "payload": {
        "target_counsel_id": "DefendantCounselAgent",
        "question_text": "Counsel, can you clarify how your client's actions align with clause 3.b of the aforementioned contract?"
      },
      "timestamp": "..."
    }
    ```

### 4.5. Manager to Counsel (Relay Question)

*   **Purpose:** The Manager relays the Judge's question to the targeted counsel agent.
*   **Message:**
    ```json
    {
      "sender_agent_id": "CourtroomSimulationManagerAgent",
      "receiver_agent_id": "DefendantCounselAgent",
      "message_type": "QUERY",
      "event_type": "QUESTION_RELAYED_TO_COUNSEL",
      "payload": {
        "question_text": "Counsel, can you clarify how your client's actions align with clause 3.b of the aforementioned contract?",
        "from_judge": true,
        "time_limit_seconds": 60
      },
      "timestamp": "..."
    }
    ```

### 4.6. Counsel to Manager (Respond to Question)

*   **Purpose:** A counsel agent submits its response to a question.
*   **Message:**
    ```json
    {
      "sender_agent_id": "DefendantCounselAgent",
      "receiver_agent_id": "CourtroomSimulationManagerAgent",
      "message_type": "RESPONSE",
      "event_type": "RESPONSE_TO_QUESTION_SUBMITTED",
      "payload": {
        "response_text": "Your Honor, my client's actions are consistent with clause 3.b because..."
      },
      "timestamp": "..."
    }
    ```

### 4.7. Judge to Manager (Deliver Verdict)

*   **Purpose:** The Judge agent submits its final verdict and reasoning.
*   **Message:**
    ```json
    {
      "sender_agent_id": "JudgeAgent",
      "receiver_agent_id": "CourtroomSimulationManagerAgent",
      "message_type": "DATA",
      "event_type": "VERDICT_DELIVERED_BY_JUDGE",
      "payload": {
        "prevailing_party": "Plaintiff",
        "reasoning": "The evidence presented clearly shows a breach of contract by the Defendant, specifically regarding failure to meet the agreed delivery timeline...",
        "damages_awarded": null // Or a specific amount if part of simulation
      },
      "timestamp": "..."
    }
    ```

### 4.8. Manager to User (Simulation Update/Output)

*   **Purpose:** The Manager sends information to be displayed to the end-user.
*   **Message:**
    ```json
    {
      "sender_agent_id": "CourtroomSimulationManagerAgent",
      "receiver_agent_id": "UserInterface", // Or a generic user-facing component
      "message_type": "STATUS", // Could also be 'DATA' for final verdict
      "event_type": "SIMULATION_UPDATE",
      "payload": {
        "update_type": "MESSAGE_FROM_AGENT", // Other types: 'PHASE_CHANGE', 'FINAL_VERDICT', 'SYSTEM_MESSAGE'
        "speaker": "PlaintiffCounselAgent", // Could be 'JudgeAgent', 'System', etc.
        "content": "The defendant's actions clearly demonstrate a breach of contract...",
        "phase_name": "Plaintiff Main Argument"
      },
      "timestamp": "..."
    }
    ```

## 5. Control Signals vs. Data Payloads

*   **Control Signals:** These messages are primarily defined by their `message_type: 'CONTROL'` and a specific `event_type`. Their `payload` might be minimal or `null`. Their main purpose is to trigger actions or phase transitions.
    *   Examples:
        *   `event_type: 'START_PHASE', payload: { phase_name: 'OPENING_STATEMENTS' }`
        *   `event_type: 'PROMPT_FOR_REBUTTAL', payload: { time_limit_seconds: 60 }`
        *   `event_type: 'BEGIN_DELIBERATION'` (payload might be null)
        *   `event_type: 'END_SIMULATION'`
*   **Data Payloads:** These messages, typically `message_type: 'DATA'` or `message_type: 'RESPONSE'`, carry substantial content generated by an agent. The `payload` is rich with the information being conveyed.
    *   Examples: `ARGUMENT_SUBMITTED`, `RESPONSE_TO_QUESTION_SUBMITTED`, `VERDICT_DELIVERED_BY_JUDGE`.

## 6. Error Message Handling

If an agent encounters an internal error or cannot process a received message, it should report this back to the `CourtroomSimulationManagerAgent`.

*   **Error Message Structure:**
    ```json
    {
      "sender_agent_id": "PlaintiffCounselAgent", // Agent that encountered the error
      "receiver_agent_id": "CourtroomSimulationManagerAgent",
      "message_type": "ERROR",
      "event_type": "AGENT_PROCESSING_ERROR", // Or more specific error event
      "payload": {
        "original_message_id": "...", // Optional: ID of the message that caused the error
        "error_code": "INTERNAL_LLM_FAILURE", // Or 'INVALID_MESSAGE_FORMAT', 'TIMEOUT_EXCEEDED'
        "error_message": "LLM failed to generate a response within the expected parameters.",
        "details": { /* Optional: further technical details */ }
      },
      "timestamp": "..."
    }
    ```
*   The Manager, upon receiving an error, would decide how to proceed:
    *   Log the error.
    *   Retry the operation if applicable (with caution).
    *   Inform the user of a problem.
    *   Potentially end the simulation gracefully if the error is critical.

## 7. ADK Considerations

The practical implementation of passing these JSON messages between ADK agents depends on the specific ADK architecture:

*   **`SequentialWorkflowAgent` (for the Manager):**
    *   When the Manager (a `SequentialWorkflowAgent`) calls another agent (e.g., `PlaintiffCounselAgent.generate_argument(params)`), the `params` dictionary can directly represent the `payload` of a `CONTROL` or `QUERY` message.
    *   The return value from the agent method (e.g., `argument_text = PlaintiffCounselAgent.generate_argument(...)`) can represent the `payload` of a `DATA` or `RESPONSE` message.
    *   The Manager would then wrap this payload into the full JSON message structure (adding sender/receiver IDs, message type, event type, timestamp) for logging or relaying if needed.
*   **Message Passing System:**
    *   If the ADK provides a more explicit message bus or queue system for inter-agent communication, agents would construct the full JSON message and publish it to the bus, addressed to the target agent. The target agent would subscribe to messages directed to it.
*   **ADK Agent `invoke` Method:**
    *   ADK agents often have a standard `invoke` method. The input to `invoke` could be the full JSON message object (as a string or dictionary). The agent's `invoke` method would then parse this message, perform actions based on `message_type` and `event_type`, and return a response message in the same JSON format.

Regardless of the exact mechanism, the key is that the *content* being exchanged conforms to the defined JSON structures.

## 8. Clarity and Maintainability

Adhering to a well-defined, consistent message structure is paramount for:

*   **Clarity:** Everyone involved in development understands how agents communicate.
*   **Maintainability:** Changes to one agent's internal logic are less likely to break communication with others, as long as the message "contract" is respected.
*   **Debugging:** Standardized message formats make it easier to log, inspect, and debug the flow of information through the system.
*   **Scalability:** As new agents or functionalities are added, they can integrate more smoothly by adopting the existing communication protocols.

These protocols serve as a foundational layer for building a robust and understandable multi-agent system for the AI Courtroom.
